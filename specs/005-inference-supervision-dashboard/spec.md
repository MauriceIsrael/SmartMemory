# Feature Specification: Inference Supervision Dashboard

**Version**: 1.0
**Status**: Draft
**Author**: Gemini
**Last Updated**: 2025-11-27

## 1. Introduction

### 1.1. Feature Description

This document outlines the requirements for an "Inference Supervision Dashboard," a web-based interface for monitoring and administering the `SmartMemory` Semantic Memory system. The application will provide real-time insights into the knowledge graph, allow for the management of inference rules, and offer administrative controls over the inference engine.

### 1.2. Problem Statement

The `SmartMemory` system currently lacks a user-friendly interface for monitoring and administration. Developers and administrators have no visibility into the state of the knowledge graph, the performance of inference rules, or a simple way to control the system's behavior. This inhibits effective debugging, optimization, and day-to-day management.

### 1.3. Goals

*   Provide a centralized dashboard for at-a-glance system health monitoring.
*   Enable users to explore and understand the facts within the knowledge graph.
*   Allow administrators to control the behavior of the inference engine by managing rules.
*   Provide a simple interface for manually triggering system processes.
*   Deliver a modern, responsive, and intuitive user experience.

### 1.4. Non-Goals

*   This feature will not support creating or editing inference rules directly through the UI. It only supports toggling their state.
*   This feature will not provide deep-graph visualization or complex graph traversal tools. It is focused on tabular data and key metrics.
*   This feature does not include user authentication or role-based access control in its initial version.

## 2. User-Centric Design

### 2.1. Target Audience

*   **ML Engineer/Administrator**: Responsible for the health and performance of the `SmartMemory` system. Needs to monitor metrics, manage rules, and trigger inference runs.
*   **Data Scientist/Analyst**: Interested in exploring the facts (both asserted and inferred) within the knowledge graph to understand the system's knowledge base.

### 2.2. User Scenarios

#### Scenario 1: Daily System Health Check

*   **As an ML Engineer**, I want to open the dashboard and immediately see key performance indicators (KPIs).
*   **Steps**:
    1.  Navigate to the dashboard's main page.
    2.  View cards displaying: Total Facts, Percentage of Inferred Facts, and Number of Active Rules.
    3.  Confirm that the system is operating within expected parameters.

#### Scenario 2: Investigating an Inferred Fact

*   **As a Data Scientist**, I want to understand why a specific fact exists in the graph.
*   **Steps**:
    1.  Navigate to the "Fact Explorer" page.
    2.  Use the search bar to find a fact of interest.
    3.  Observe a visual badge indicating the fact was "Inferred".
    4.  Review the fact's provenance metadata to understand which rule generated it.

#### Scenario 3: Disabling a Noisy Inference Rule

*   **As an ML Engineer**, I have noticed a rule is generating incorrect or irrelevant facts and I want to disable it.
*   **Steps**:
    1.  Navigate to the "Inference Rules" page.
    2.  Identify the problematic rule in the list.
    3.  Review its statistics (e.g., `triples_generated`).
    4.  Click the toggle switch to deactivate the rule.
    5.  Receive a visual confirmation (e.g., a toast notification) that the rule has been disabled.

#### Scenario 4: Manually Running Inference

*   **As an Administrator**, I want to trigger an inference run after making a system change.
*   **Steps**:
    1.  Navigate to the "Administration" console page.
    2.  Click the "Run Inference" button.
    3.  See a loading indicator while the process is running.
    4.  Receive a notification upon completion.

## 3. Functional Requirements

### 3.1. Dashboard View

*   **FR-3.1.1**: The system must display a dashboard page.
*   **FR-3.1.2**: The dashboard must show a "Total Facts" card with the total count of triplets in the graph.
*   **FR-3.1.3**: The dashboard must show an "Inferred Facts" card with the count and percentage of facts that were generated by rules.
*   **FR-3.1.4**: The dashboard must show an "Active Rules" card with the count of currently active inference rules.
*   **FR-3.1.5**: The dashboard should include a graph displaying the cumulative number of facts (triplets) created over time (e.g., last 30 days).

### 3.2. Fact Explorer

*   **FR-3.2.1**: The system must provide a "Fact Explorer" page that displays facts in a paginated table.
*   **FR-3.2.2**: The fact table must display the Subject, Predicate, and Object of each triplet.
*   **FR-3.2.3**: The system must provide a text search input to filter facts based on their subject, predicate, or object.
*   **FR-3.2.4**: Each fact in the table must have a visual indicator (e.g., a badge) to distinguish between "Asserted" (manually added) and "Inferred" (generated by a rule) facts.

### 3.3. Inference Rule Management

*   **FR-3.3.1**: The system must provide a "Rule Management" page that lists all available inference rules.
*   **FR-3.3.2**: For each rule, the list must display its ID, description, and current status (Active/Inactive).
*   **FR-3.3.3**: The system must allow a user to view the full SPARQL query for any rule.
*   **FR-3.3.4**: For each rule, the system must display its execution statistics, including execution count and the number of triples it has generated.
*   **FR-3.3.5**: Each rule in the list must have a toggle control to activate or deactivate it.
*   **FR-3.3.6**: The system must provide immediate visual feedback (e.g., a toast notification) when a rule's state is changed.

### 3.4. Administration Console

*   **FR-3.4.1**: The system must provide an "Administration" page.
*   **FR-3.4.2**: The administration page must contain a button to manually trigger a full inference run.
*   **FR-3.4.3**: The system must display a loading indicator while the manual inference process is active.
*   **FR-3.4.4**: The system must display logs from the last inference run on the Administration page.

### 3.5. General UI/UX

*   **FR-3.5.1**: The application must feature a primary navigation sidebar for switching between the Dashboard, Fact Explorer, Rule Management, and Administration pages.
*   **FR-3.5.2**: The interface must be responsive and usable on standard desktop screen sizes.
*   **FR-3.5.3**: The application must feature a "dark mode" theme.
*   **FR-3.5.4**: The UI must handle API errors gracefully, informing the user of any connectivity or server-side issues.

## 4. Non-Functional Requirements

*   **NFR-4.1**: **Performance**: Page loads and state changes (like toggling a rule) should complete in under 2 seconds.
*   **NFR-4.2**: **Usability**: The interface should be intuitive enough for a new user from the target audience to understand and use without extensive training.
*   **NFR-4.3**: **Aesthetics**: The UI should have a modern, "premium" feel with smooth transitions and a clean layout.

### 4.4. Edge Cases and Error States

*   **Error State - API Unreachable**: If the frontend cannot connect to the backend API, it must display a clear, persistent error message and disable UI elements that require a connection.
*   **Empty State - No Facts**: If the knowledge graph contains no facts, the "Fact Explorer" should display a user-friendly message instead of an empty table.
*   **Empty State - No Rules**: If no inference rules are defined in the system, the "Rule Management" page should display a clear message.
*   **Error State - Rule Validation Error**: If a rule has a `validation_error`, the UI should visually distinguish this rule and provide a way for the user to see the error details (e.g., in a tooltip or modal).
*   **Loading State - Slow API**: If an API call is taking longer than expected (e.g., >3 seconds), the UI should show a more descriptive loading message.

## 5. Success Criteria

*   **SC-5.1**: An administrator can successfully view system stats, browse facts, and enable/disable a rule within 5 minutes of first using the application.
*   **SC-5.2**: The dashboard accurately reflects the real-time state of the `SmartMemory` system with a maximum latency of 10 seconds.
*   **SC-5.3**: The "Fact Explorer" can successfully render and filter a dataset of at least 100,000 facts with acceptable performance (paginated response under 3 seconds).
*   **SC-5.4**: A user action to toggle a rule's state is successfully reflected in the backend and UI within 2 seconds.
*   **SC-5.5**: The manual "Run Inference" button successfully triggers the backend process and provides clear feedback of its execution state (in-progress, success, failure).

## 6. Assumptions and Dependencies

### 6.1. Assumptions

*   It is assumed that the `SemanticMemoryServer` instance and its components (`ProvenanceGraph`, `RuleEngine`) are programmatically accessible from the new backend API.
*   It is assumed that the existing `InferenceRule` objects contain all the necessary data fields required by the UI (`id`, `description`, `sparql_query`, `is_active`, `execution_count`, `triples_generated`).
*   It is assumed that facts in the `ProvenanceGraph` have queryable metadata to distinguish between asserted and inferred origins.

### 6.2. Dependencies

*   This project is dependent on the existing `SmartMemory` Python backend.
*   The functionality of the dashboard is directly tied to the availability and performance of the backend API that will be built.

## 7. Key Entities & Data Model

*   **Fact (Triplet)**:
    *   `Subject`: (string)
    *   `Predicate`: (string)
    *   `Object`: (string)
    *   `Provenance`: (string, e.g., "user" or "sparql-rule-id")
*   **Inference Rule**:
    *   `id`: (string)
    *   `description`: (string)
    *   `sparql_query`: (string)
    *   `is_active`: (boolean)
    *   `execution_count`: (integer)
    *   `triples_generated`: (integer)
    *   `validation_error`: (string, nullable)
*   **System Stats**:
    *   `total_triplets`: (integer)
    *   `inferred_triplet_count`: (integer)
    *   `asserted_triplet_count`: (integer)
    *   `active_rule_count`: (integer)
    *   `inactive_rule_count`: (integer)
