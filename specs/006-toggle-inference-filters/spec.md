# Feature Specification: Manage Inference Engines and Filters

**Feature Branch**: `001-toggle-inference-filters`
**Created**: 2025-11-28
**Status**: Draft
**Input**: User description: "l'administration console de l'application de supervision doit permettre d'activer ou non les 2 moteurs d'inference. Au moment de l'activation les regles correspondantes sont chargées. Dans Rule management, j'aimerais pouvoir filtrer les règles pour ne voir que celles qui ont été chargées a posteriori. Idem dans les Fact je voudrais pouvoir filtrer pour charger ceux inférés"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Toggle Inference Engines (Priority: P1)

As an administrator, I want to activate or deactivate the inference engines from a central console so that I can control the system's reasoning capabilities and resource usage.

**Why this priority**: This is the core functionality that enables or disables the entire set of features related to inference. Without it, the other stories are irrelevant.

**Independent Test**: This can be tested by accessing the administration console, toggling an engine's state, and verifying that the system correctly reports the new state (e.g., in a log or status indicator).

**Acceptance Scenarios**:

1.  **Given** the administration console is open and an inference engine is "disabled", **When** the administrator toggles the engine to "enabled", **Then** the system activates the engine and loads its associated rules.
2.  **Given** the administration console is open and an inference engine is "enabled", **When** the administrator toggles the engine to "disabled", **Then** the system deactivates the engine and unloads its associated rules.

---

### User Story 2 - Filter Dynamically Loaded Rules (Priority: P2)

As an administrator, I want to filter the rules list to see only those that were loaded dynamically, so that I can easily distinguish them from the system's default rules.

**Why this priority**: This provides crucial visibility into the impact of activating an inference engine, allowing the admin to manage and review the active rule set.

**Independent Test**: Can be tested by navigating to the "Rule Management" view, applying the filter, and verifying that only the rules from the activated engine are displayed.

**Acceptance Scenarios**:

1.  **Given** an inference engine is active and its rules are loaded, **When** the administrator applies the "Dynamically Loaded" filter in "Rule Management", **Then** the view updates to show only the rules associated with the active engine.
2.  **Given** no inference engines are active, **When** the administrator applies the "Dynamically Loaded" filter, **Then** the rule list is empty.

---

### User Story 3 - Filter for Inferred Facts (Priority: P3)

As an administrator, I want to filter the facts list to see only the facts that were generated by an inference engine, so that I can analyze the output of the reasoning process.

**Why this priority**: This allows the administrator to validate the results of the inference process and understand how the knowledge graph is being augmented.

**Independent Test**: Can be tested by navigating to the "Facts" view, applying the filter, and verifying that only facts marked as "inferred" are displayed.

**Acceptance Scenarios**:

1.  **Given** an inference engine has generated new facts, **When** the administrator applies the "Inferred" filter in the "Facts" view, **Then** the view updates to show only the inferred facts.
2.  **Given** no facts have been inferred, **When** the administrator applies the "Inferred" filter, **Then** the facts list is empty.

---

### Edge Cases

-   What happens if an administrator tries to activate an engine that fails to load its rules? The system should provide a clear error message and revert the engine to a "disabled" state.
-   How does the system handle an administrator toggling an engine on and off rapidly? The system should handle these requests gracefully, ensuring a consistent final state.

## Requirements *(mandatory)*

### Functional Requirements

-   **FR-001**: The system MUST provide a UI in the administration console to enable or disable each of the two inference engines.
-   **FR-002**: The state of each inference engine (enabled/disabled) MUST be persisted across application restarts.
-   **FR-003**: When an inference engine is enabled, the system MUST load its associated inference rules.
-   **FR-004**: When an inference engine is disabled, the system MUST unload its associated inference rules.
-   **FR-005**: The "Rule Management" interface MUST provide a mechanism to filter the displayed rules to show only those loaded dynamically by an administrator.
-   **FR-006**: The "Facts" interface MUST provide a mechanism to filter the displayed facts to show only those generated by an inference engine.
-   **FR-007**: The system MUST provide clear visual feedback to the administrator indicating the current state (enabled, disabled, error) of each inference engine.
-   **FR-008**: The system MUST identify the two inference engines as "OWL-RL Engine" and "SPARQL Engine" in the administration console.

### Key Entities

-   **Inference Engine**: Represents a reasoning module that can be activated or deactivated. Has an associated set of rules.
-   **Rule**: A single inference rule. Can be either a "default" system rule or a "dynamically loaded" rule.
-   **Fact**: A triple in the knowledge graph. Can be either an "explicit" fact or an "inferred" fact.

## Success Criteria *(mandatory)*

### Measurable Outcomes

-   **SC-001**: An administrator can successfully enable or disable an inference engine in under 15 seconds.
-   **SC-002**: The UI correctly reflects a change in an engine's state within 3 seconds of the administrator's action.
-   **SC-003**: Applying a filter to the "Rule Management" or "Facts" view displays the filtered results in under 3 seconds.
-   **SC-004**: The system can successfully load or unload a set of 100 rules associated with an engine in under 10 seconds.

## Assumptions

-   The application already has an "administration console", a "Rule management" page, and a "Facts" view. This feature enhances existing views.
-   "A posteriori" loaded rules are defined as any rules loaded by an administrator action after the application has started, as opposed to rules loaded at system startup.
-   The filtering on facts is for display purposes within the UI and does not alter the underlying data in the knowledge graph.
